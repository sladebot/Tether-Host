## Selected architecture and prerequisite gate

`Tether → existing tailnet → guest HTTPS Serve :443 → guest 127.0.0.1:8642 → non-admin guest Hermes → guest-local OpenAI subscription credentials`

Computer use executes inside the guest's interactive non-admin desktop. The Studio is not an API proxy. oMLX remains deferred; do not start it or open an inference exception. Preserve the old Studio endpoint and app profile until acceptance passes.

Before any provider sign-in or agent execution, the main migration must prove external IPv4/IPv6 enforcement against Studio/LAN access, tailnet containment, persistence after reboot/reload, no host mounts or clipboard, and a non-admin runtime. The migration record currently reports incomplete isolation and an administrator guest account. A single IPv4 probe is not this gate. Guest receipt of phone connections must remain possible while guest-initiated access to Studio and unrelated peers is denied. Replies to permitted incoming connections are not unsolicited outbound access.

## Guest setup sequence after isolation passes

1. In the chosen **non-admin guest account**, record `id`, `hermes --version`, `hermes gateway --help`, `hermes computer-use status`, and guest Tailscale version/status. Record executable paths, guest identity and exact checkout commit when available. Never infer compatibility from a version number alone.
2. Verify this runtime's home/config is separate from the provisioning account. No copied Studio credentials, OAuth caches, browser profiles or MCP configurations. Check that no other guest gateway already owns the API port before starting one.
3. Run `hermes model` inside this runtime and select the requested OpenAI → ChatGPT or Codex Subscription flow. Obtain fresh user sign-in; the expired migration code cannot be reused. Discover actual supported models afterward. No paid API fallback, Nous login or oMLX setup in this phase.
4. Configure this runtime's protected Hermes environment with `API_SERVER_ENABLED=true`, `API_SERVER_HOST=127.0.0.1`, `API_SERVER_PORT=8642` and a **fresh guest-specific** `API_SERVER_KEY`. Keep the key out of this document, logs and screenshots. Do not assume the existing Studio `~/hermes_token` is the guest credential. Configure the installed version's supported gateway lifecycle in this same account; verify ownership and listening addresses after startup. [Hermes API Server](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)
5. In the guest, check installed `tailscale serve --help`, then configure guest Serve with `tailscale serve --bg --https=443 http://127.0.0.1:8642`. Read back Serve status and obtain the guest's exact DNS name; do not construct it from the display name. Verify Funnel is off **for the guest**. The Studio's existing Serve/Funnel services are unrelated and unchanged. Serve supplies private-tailnet HTTPS while Hermes still verifies its own bearer key. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)
6. Enable the guest `computer_use` toolset using `hermes tools`; check it is available on the API-server platform. Run `hermes computer-use doctor` in the non-admin interactive session. Validate version, MCP, Accessibility and actual screen capture. The prior admin session's success does not prove these checks pass in another account. Start with standard approvals; do not enable YOLO as a diagnostic shortcut. Current official docs describe standard CuaDriver.app and private bounded/unrestricted runtimes with different permission identities. [Computer Use](https://hermes-agent.nousresearch.com/docs/user-guide/features/computer-use)
7. Create a separate Tether API Server connection to `https://<verified-guest-dns-name>` and provision the guest token into its origin-bound Keychain entry. Preserve the old connection, conversation IDs and pending work; no automatic migration of host run IDs to the guest.

## API release gate

After setup, verify each response against the **guest**, both on guest loopback and from the allowed phone over HTTPS. Bound diagnostics to 10 seconds per ordinary request; discovery of model options may use 30 seconds. A timeout is not proof of isolation without independent listener/route evidence.

| Check | Required evidence |
|---|---|
| `/health` | Guest version and successful liveness; distinguish from Studio |
| `/v1/capabilities` anonymously / wrong token | Rejected, normally 401 |
| `/v1/capabilities` with guest token | Hermes platform; required bearer; run submission/status/events/stop; durable idempotency with recorded retention |
| Approval / steering | Advertised flags and endpoint paths before enabling controls |
| `/health/detailed` | API/model/state readiness inspected, not HTTP 200 alone |
| `/api/model/options` | Requested subscription provider authenticated; real discovered model IDs |
| `/v1/toolsets` | Guest computer-use availability; no host remote-control integration |
| Guest listen sockets | API only loopback; phone uses guest Serve, not guest LAN :8642 |
| DNS/TLS | Exact guest hostname resolves on phone; valid certificate; no insecure TLS override |

Record redacted capability JSON, versions, timestamps and test IDs. API bearer values, OAuth codes and user conversation contents are excluded from evidence artifacts.

## Concrete Tether integration gaps found in current source

These findings come from `Tether/Services/HermesAPIClient.swift` and `Tether/App/AppModel.swift`. The capability check below was subsequently implemented in the client; other findings require integration/verification by their owners.

- **Handshake repaired:** API Server `testConnection()` now requires `run_submission`, `run_status`, `run_events_sse`, and `run_stop` to be true, plus `runs_idempotency.supported/durable` true and positive `retention_seconds`. Capability 404 no longer passes via models; missing support produces `durableRunsUnavailable`. Dashboard testing remains separate. `requireDurableRuns()` exposes the same gate for existing saved profiles; callers must invoke it before new durable submissions rather than relying on a past connection check. This verifies advertised support, not actual isolation or reboot survival. Older servers without discovery/durable admission are intentionally rejected for this API Server workflow. Flags match the [upstream capability handler](https://github.com/NousResearch/hermes-agent/blob/main/gateway/platforms/api_server.py).
- **Mutable chat retry payload:** `PendingRun` freezes text/history but creation reads `selectedModelChoice` again. Changing model between ambiguous submission and retry can conflict with the saved idempotency key. Persist the exact model/provider/session/origin at submission.
- **Unbounded missing-run/conflict retries:** mini-app and chat loops categorize 404/409 as network failures. Distinguish expired/unknown run and admission conflict; retain evidence and provide an explicit recovery action without silently creating a replacement job.
- **Migration provisioning:** Debug environment bootstrap imports only when there are no saved connections. Reinstalling the phone with guest environment variables will not replace its existing host profile. Add a separate guest connection explicitly.
- **Resume feature limitations:** mini jobs persist one active build and poll approvals/results. Terminal failure clears the job record. Expose a recoverable failure/history entry; verify no lost edits or duplicate revision when persistence is interrupted.
- **Client-owned histories:** `createRun` supplies `conversation_history`. This does not automatically incorporate later server-side child results. Server session-history reconciliation is a separate integration requirement for detached subagents.
- **CUA result presentation:** the app receives text/progress; no guest live-desktop viewer is established by this architecture. Verify a guest-side capture artifact independently rather than claiming a rendered screenshot was delivered to Tether.

## Bounded end-to-end tests, only after the isolation gate

Use a dedicated test conversation and disposable guest scratch files. Maximum five minutes per agent test, then inspect status or stop that specific test run. Keep keys and exact payloads long enough to verify replay.

1. **Chat:** request a fixed short phrase using the discovered subscription provider/model. Confirm completed run and matching output through phone-to-guest HTTPS.
2. **Admission ambiguity:** repeat one exact submitted body/key; verify same run ID. A deliberately changed test body under that key must conflict. Confirm only one execution using its scratch marker.
3. **App close:** request a harmless delayed counter mini app, wait for server acceptance/run ID, force-close Tether and reopen after the server completes. Confirm one artifact, complete HTML, and no second run. Repeat with network lost before acknowledgement; verify saved-key retry.
4. **Edit:** change a label through mini-app chat, close/reopen during execution, verify one updated revision and working rollback to the original. Check offline preview and isolation policy.
5. **Approval:** invoke a pre-agreed benign approval-gated guest action. Disconnect before approving; recover command/choices/request ID from run status, deny it and confirm the action did not execute. Do not manufacture a dangerous action solely to trigger approval.
6. **Steer/stop:** steer an active disposable test once, then separately stop a delayed test. Check stopping/terminal state; do not replay uncertain steering blindly.
7. **Guest-only CUA:** prepare an empty guest TextEdit document with a unique visible marker. Ask Hermes to inspect and type a test phrase only there. Verify marker/phrase in guest capture and unchanged Studio desktop. Re-run doctor after guest logout/login; record expected behavior while locked.
8. **Server restart:** with only a disposable run active, planned guest gateway restart should yield truthful interrupted/recoverable status, not a never-ending spinner or automatic duplicate. Do not promise worker continuation through VM shutdown.
9. **Final migration:** run fresh connection/chat/build/edit/close-reopen on the reinstalled phone. Reconfirm guest isolation after reboot and preservation of unrelated device connectivity before declaring migration complete.

The upstream run implementation separates worker state from SSE buffers and marks orphaned durable runs interrupted after owner restart. Use authoritative polling after a stream disconnect. App-close recovery and server-crash recovery are different guarantees. [Run implementation](https://github.com/NousResearch/hermes-agent/blob/main/gateway/platforms/api_server_runs.py)
